# HaoChen 无人酒店 Agent 核心服务端架构选型

状态：accepted（P0.1 评审通过，2026-09-27；验收主张结果列随各阶段 Gate 回填）
类型：architecture
Owner：docs/design.md

## 问题

HaoChen 无人酒店需要一套 Agent 核心服务端支撑三端：C 端小程序提供咨询、房型查询、预订、改期、取消、发票、客房需求、退房、投诉与周边推荐；保洁小程序接收清洁派单、执行退房改密留证与打卡；管理后台完成 Agent 配置与管理、会话监控、风险告警、数据报表、智能体日志、酒店基础数据与记忆管理。项目同时要求 Agent 运行好坏可视化，并以数据中心持续提升数据质量。

当前仓库没有酒店域代码与数据。从零自研需要重新解决请求串行、运行恢复、租约、审计、检索治理与评估这些已有成熟实现的问题；门锁密码、视觉审核与派单又是酒店场景特有的新风险面，需要明确的信任边界与验收方式。需要一次架构选型确定技术底座、领域边界与验证路径。

## 提案

酒店 Agent 核心服务端采用以下技术底座：分层边界（薄路由、services 用例、repositories 持久化）、Request/Run 两阶段状态模型与线程 FIFO、LangGraph 中间件流水线、五套存储分工、两段式检索、双评估体系与本地审计加 Langfuse 的观测方式。

在此基础上新增酒店域：门锁密码生命周期（明文不落库、每日轮换、续订保持、退房强制轮换）、客房派单状态机与留证、机器人配送、打卡视觉审核、mcp-gateway 外部系统网关，以及以质检标注到评估回归为主线的数据中心。完整设计、领域模型和关键链路由 Owner 文档拥有。

## 替代方案

- 从零自研轻量单体（FastAPI + PostgreSQL + 定时脚本）：依赖最少，但请求串行、运行租约、崩溃恢复、审计与评估全部需要重造，运行可视化失去现成派生基础；拒绝。
- 采用托管 SaaS 智能客服平台：上线快，但房态、门锁、派单与打卡需要深度业务集成，数据主权与二次开发受限；拒绝。
- 直接分叉开源 Agent 平台全量仓库并裁剪：省去初始选型，但裁剪与升级路径都要长期维护，酒店域仍需自建；拒绝。
- 只在对话层接入通用大模型 API 并自行编排工具：实现简单，但缺少 Run 级审计、评估与队列治理，无法满足可视化与数据质量要求；拒绝。

## 风险

门锁、机器人与微信支付的接口差异由 mcp-gateway 收敛；接入前需要逐一验证真实设备协议、回调签名与失败语义，无法对接时保留人工前台通道。

房间密码经对话下发给客人，存在被转发泄露的暴露面；依赖凭证有效期、每日轮换与退房轮换收窄窗口，客服侧不主动复述历史密码。

打卡视觉审核受光照与遮挡影响；未通过记录进入人工复核，系统不提供静默通过路径。

数据中心依赖标注质量；评估集冷启动阶段先用真实质检标注与 FAQ 抽样构建最小集合，逐步扩充。

方案自 P0.1 评审通过后进入实现：P0 基建（契约 mock、compose、CI、三端脚手架）、P1 运行时不变量（请求接入 FIFO、租约恢复、审计、SSE 与恢复演练）与 P3 知识库咨询链路（两段式检索、知识库评估基线、C 端咨询页的流式会话、引用展示、点赞点踩与转人工登记）已交付；验收矩阵各条仍为 Not run，待对应阶段 Gate 逐条取证回填。
