状态：draft v0（未真机验证，未验证项登记见 §7；P0.2 预研结论与人工兜底清单见 §9）

适用范围：local/staging 的契约 mock（`backend/app/device_sim`）与 P4 起的真实接入实现都以本文为准；实现与契约不一致时，先改契约再改代码。

## 1. 通用约定

### 1.1 传输与编码

- HTTP + JSON（UTF-8），`Content-Type: application/json`；成功返回 2xx，失败统一用 §1.3 错误体。
- 时间：RFC3339 UTC（如 `2026-09-27T08:00:00Z`）；金额：整数（分）；房间号、订单号：字符串（禁止数值转换与截断）。
- 平台标识：房间号跨系统统一为 `room_no`，订单跨系统统一为 `order_no`，两者在门锁、机器人、支付、PMS 侧使用同一值。

### 1.2 幂等

- 写接口由调用方生成幂等键（`业务对象号 + 操作名`，如 `order_no:pay`、`housekeeping_task_id:rotate`），经请求体 `idempotency_key` 字段传递。
- 服务端按 `(接口, 幂等键)` 去重：重复请求返回首次结果（同状态码与响应体），不重复产生副作用。
- 我方接收回调时的幂等键：支付用 `transaction_id`，机器人状态用 `delivery_id + status`；重复投递不产生第二事实（验收主张 A3）。
- 幂等记录保留期 ≥ 7 天；超期重复按新请求处理。

### 1.3 错误模型

```json
{"error": {"code": "credential_not_found", "message": "房间无有效凭证", "retryable": false}}
```

| HTTP | code | 语义 | retryable |
| --- | --- | --- | --- |
| 400 | `invalid_request` | 参数缺失或非法 | false |
| 401/403 | `unauthorized` / `forbidden` | 身份或权限不满足 | false |
| 404 | `*_not_found` | 对象不存在（房间、凭证、订单、配送单） | false |
| 409 | `conflict` | 状态冲突（如重复轮换的版本竞争） | false |
| 429 | `rate_limited` | 触发限流 | true |
| 502/503 | `upstream_error` | 外部系统不可用 | true |
| 504 | `timeout` | 超时 | true |

判定规则：`retryable=false` 的失败不得重试，由业务层转为用户可见结果或转人工；只有 `retryable=true` 才进入 §1.4 重试策略。

### 1.4 超时与重试

- 连接超时 2s、读超时 5s（门锁开锁类 3s）；超时按 `timeout` 失败处理。
- 重试：指数退避 + 抖动，最多 3 次，总预算 ≤ 30s；**写操作重试必须在幂等键保护下执行**。
- 回调（我方作为接收方）：假定至少一次投递，必须幂等；真实渠道重试间隔由渠道决定，mock 用 `times` 参数模拟（§4.3）。

### 1.5 回调签名

- mock 约定：对回调 JSON 体做规范化序列化 `json.dumps(body, sort_keys=True, ensure_ascii=False)`（UTF-8 字节），以 `DEVICE_SIM_SIGNING_SECRET` 为密钥 HMAC-SHA256，十六进制摘要放 `X-Sim-Signature` 头。
- 真实渠道签名（微信支付 APIv3 证书签名等）与平台无关，接入时按渠道规范实现；差异登记见 §7。
- 接收方先验签、后落库；验签失败返回 401 且不产生任何事实。

### 1.6 故障注入（仅 mock）

| 模式 | 行为 | 用途 |
| --- | --- | --- |
| `error` | 立即返回指定错误码（默认 503，体为 `{"error": "injected_fault", ...}`） | 失败分支与负向用例 |
| `timeout` | 延迟 `sleep_seconds` 后按正常逻辑处理 | 超时、慢链路、lease 收敛演练 |
| `malformed` | 返回非法 JSON 响应体（HTTP 200） | 解析健壮性 |

- 配置：`POST /faults/v1/config`（`{"system": "lock|robot|wechat", "mode": "...", "status_code": 503, "sleep_seconds": 30, "remaining": null}`）；`remaining` 为空表示持续生效，给定次数后自动失效。
- 查询 `GET /faults/v1/config`、清除 `DELETE /faults/v1/config`；`POST /admin/v1/reset` 重置全部 mock 状态（测试用例间隔离用）。
- 重置会清空设备侧版本计数器：若平台库中已有该房间的凭证行，重置后重新签发会从版本 1 起算并与本地 `(room_no, version)` 唯一约束分叉（显式报冲突，不静默复用旧码）。联调重置 mock 时须同时清理平台侧该房间的凭证行，或改用未使用过的房间。
- 业务代码不得感知故障注入；mock 与真实实现的差异只允许存在于传输层与本文登记项内。

## 2. 门锁凭据服务（/lock/v1）

### 2.1 数据模型

| 字段 | 说明 |
| --- | --- |
| `credential_id` | 凭证 ID（幂等与审计引用） |
| `room_no` | 房间号 |
| `code` | 明文密码，**仅存在于设备侧与签发响应载荷**；平台数据库只存 `code_hash` 与生效窗口 |
| `version` | 同房间单调递增（每次签发/轮换/预生成 +1；吊销后重新签发继续递增、不回退） |
| `status` | `active` / `next` / `revoked` |
| `reason` | `checkin` / `daily` / `renewal` / `checkout` / `leak` / `delivery` |
| `valid_from` / `valid_to` | 生效窗口；签发类接口可显式携带（缺省按 `valid_hours` 自现在起算） |

行为规则：同房间同一时刻至多一条 `active`、至多一条 `next`；新签发或轮换即把旧凭证置 `revoked`，激活 `next` 即把旧 `active` 置 `revoked`；`valid_to` 到期后 `active` 视为失效；开锁只接受"当前 `active` + 落在生效窗口内"的明文码。

每日轮换窗口口径（调用方约定，P4.7）：当日凭证 `[今日 00:00, 明日 00:00)`、次日凭证 `[明日 00:00, 后日 00:00)`，均按酒店本地时区；到点由调用方激活 `next`（不产生新明文），当日凭证缺位或窗口错位时兜底重签，次日 `next` 始终预排。真机接入时若设备侧只支持"相对时长"（`valid_hours`）而不接受绝对窗口，需按 §7 登记为待确认项并在适配层换算。

### 2.2 端点

| 方法 | 路径 | 语义 | 幂等 |
| --- | --- | --- | --- |
| POST | `/lock/v1/credentials` | 签发凭证（首次入住；`reason=renewal` 用于续订保持策略的兜底签发） | `idempotency_key` |
| POST | `/lock/v1/credentials/rotate` | 轮换（`daily` / `checkout` / `leak` / `delivery`），旧凭证立即 revoked；可携带 `expected_version`，不符返回 409 | `idempotency_key` |
| POST | `/lock/v1/credentials/revoke` | 吊销当前凭证，无凭证返回 404；可携带 `expected_version`，不符返回 409 | 天然幂等（重复吊销 404） |
| POST | `/lock/v1/credentials/next` | 预生成次日凭证（`reason=daily`，必须携带 `valid_from`/`valid_to`）；重复调用整体替换既有 next（旧 next 置 revoked） | 天然幂等（以最后一次为准，版本继续递增） |
| POST | `/lock/v1/credentials/next/activate` | 到点激活：next 转为当前凭证、旧当前凭证立即 revoked、不产生新明文；无 next 返回 404；可携带 `expected_version`，不符返回 409 | 天然幂等（激活后槽位为空，重复调用 404） |
| POST | `/lock/v1/credentials/next/revoke` | 撤销 next（泄露处置与重排），无 next 返回 404；可携带 `expected_version`，不符返回 409 | 天然幂等（重复吊销 404） |
| POST | `/lock/v1/credentials/extend` | 展期当前凭证（续订保持策略）：只改窗口终点，不换码、不换版本；可携带 `expected_version`，不符返回 409；终点不晚于起点返回 422 | 天然幂等（同窗口重复调用无副作用） |
| GET | `/lock/v1/credentials/{room_no}` | 读取凭证元数据；**mock 调试回读包含明文字段，真实门锁不提供该字段** | 只读 |
| GET | `/lock/v1/credentials/{room_no}/next` | 读取 next 元数据（同上，调试回读含明文） | 只读 |
| POST | `/lock/v1/unlock` | 开锁校验（`code` 与 `source: guest_app\|front_desk\|housekeeping`，须为窗口内 active 码），返回 `accepted` | 只记录，不去重 |
| GET | `/lock/v1/unlock-records` | 开锁记录（对账与排障；mock 返回最近 100 条） | 只读 |

失败语义：未知房间或吊销不存在的凭证 → 404；门锁不可达 → `upstream_error`；**门锁调用失败时订单不得进入 `completed`，清洁任务不得进入 `closed`（验收主张 A1 负例）**。

### 2.3 安全约束

- 明文禁止进入日志、消息历史、记忆、知识库与审计导出（由 CredentialGuard 保证）；服务端业务代码不得依赖 mock 的明文回读字段。
- 轮换与吊销调用必须携带凭证 `version`（或幂等键指向的期望版本），版本不匹配返回 409，防止旧消息重放改密。
- 下发语义：明文不可回读，客人索要密码时按需轮换（`reason=delivery`，携带期望版本）——下发即换新码、旧码立即失效；服务通知与聊天下发同为此口径。

## 3. 机器人配送服务（/robot/v1）

### 3.1 状态机

`queued → dispatching → delivering → arrived → delivered`；任意执行态可转 `failed`（附原因）；`delivered` 与 `failed` 为终态。

### 3.2 端点

| 方法 | 路径 | 语义 | 幂等 |
| --- | --- | --- | --- |
| POST | `/robot/v1/deliveries` | 创建配送单（`order_no`、`room_no`、`item`），返回 `delivery_id`、状态 `queued` | 同 `order_no` 返回既有配送单 |
| GET | `/robot/v1/deliveries/{delivery_id}` | 查询配送状态 | 只读 |
| POST | `/robot/v1/deliveries/{delivery_id}/advance` | mock 专用状态推进；真实环境由厂商状态回调替代（登记 §7） | 状态幂等（重复推进同状态无副作用） |

失败语义：`failed` 后不自动重派——由服务层决定补派新配送单或转人工；重复创建同 `order_no` 不重复派机器人。

## 4. 微信侧（/wechat/v1）

### 4.1 登录

`POST /wechat/v1/login`（`code`）→ `{openid, session_key}`。`code` 一次性；失效或重复使用 → `invalid_request`。

### 4.2 支付

| 方法 | 路径 | 语义 |
| --- | --- | --- |
| POST | `/wechat/v1/pay/orders` | 下单（`order_no`、`amount_fen`、`openid`、`description`）→ `prepay_id` + 小程序 `wx.requestPayment` 参数 |
| GET | `/wechat/v1/pay/orders/{order_no}` | 支付状态查询 |

回调（我方接收，`POST /api/webhooks/wechat/pay`）：

1. 验签（§1.5）失败 → 401，不写任何事实。
2. 验签通过 → 以 `transaction_id` 为幂等键，**先在 PostgreSQL 提交支付事实**。
3. 提交成功后再投递 worker 触发密码下发与入住指引；重复回调命中幂等键即返回成功、不产生第二单（验收主张 A3）。
4. 乱序回调（如先 `success` 后 `close`）以本地订单状态机为准，不允许回退已 `paid` 状态。

### 4.3 mock 回调模拟

`POST /wechat/v1/pay/simulate-callback`（`order_no`、`target_url`、`event: success|fail`、`times: 1–10`）→ 以 §1.5 签名把回调向 `target_url` 投递 `times` 次，返回每次投递的 HTTP 状态码（不可达时返回 `error: <异常名>`）。

用途：重复回调幂等测试、验签负例测试。真实环境不存在该端点，回调由微信侧驱动。

### 4.4 服务通知（订阅消息）

`POST /wechat/v1/notify/subscribe` → `{message_id, status}`，入参：

| 字段 | 说明 |
| --- | --- |
| `openid` | 接收人（必须是已完成订阅授权的客人） |
| `template_id` | 模板 ID；未配置时业务侧不下发（记 `skipped` 事件） |
| `page` | 点击跳转的小程序页（如订单页） |
| `data` | 语义键载荷 `{room_no, floor, code, guide}`：**模板字段映射由传输层适配**，业务代码不写死模板键 |

语义：密码下发的第二通道，仅作为「即时提醒」；密码主通道始终是订单页 / 站内消息，通知未触达不影响客人自助开门。明文约束：`code` 只随本次请求出站，客户端不打印、不缓存。

调用时机与口径（P4-T6d 落地）：

- 唯一调用点是 `checkin.prepare` durable task 中密码签发提交之后——这是明文在服务端存在的唯一时刻。
- 尽力而为、不重试：失败只登记订单事件 `credential_notified`（`status: sent|failed|skipped` + `reason` + `template_id`，**绝不记录密码**），主通道与任务结果不受影响。
- 重放（幂等键命中且当下无新明文）既不下发也不登记，避免重复打扰。

## 8. 失败语义汇总（跨系统处置口径）

失败先按 §1.3 判定 `retryable`：`true` 走自动重试（§1.4），`false` 与重试耗尽一律转下述处置。下表的「自动处置」与「人工兜底」是服务层实现与测试用例的兜底口径，各业务链路（P4 起）必须逐条覆盖。

| # | 环节 | 失败模式 | retryable | 自动处置 | 用户可见结果 | 人工兜底 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 门锁签发 / 轮换 / 吊销 | 超时、`upstream_error` | true | 幂等键保护下重试（≤3 次 / 30s） | 「密码下发中，稍后在订单页查看」 | 重试耗尽告警，前台在管理后台手动签发（P7 门锁操作，审计留痕） |
| 2 | 门锁轮换 / 吊销 | 409 版本竞争 | false | 不重试；读取当前凭证后按策略重算，仍冲突即终止 | 「状态已变化，请刷新」 | 前台核对后人工处置 |
| 3 | 门锁查询 / 吊销 | 404（无有效凭证） | false | 不重试，按业务语义处理（如退房轮换视为已完成） | 无打扰 | 无 |
| 4 | 门锁调用 | 失败（任意原因） | — | **订单不得进入 `completed`、清洁任务不得进入 `closed`（A1 负例）** | 单据停留当前态并提示 | 前台应急钥匙 / 人工开门；改密失败时保洁现场换密 |
| 5 | 机器人配送创建 / 查询 | 超时、`upstream_error` | true | 自动重试；创建按 `order_no` 幂等，重复不重派 | 「配送正在安排」 | 重试耗尽转人工派单 |
| 6 | 机器人配送 | 终态 `failed` | false | 不自动重派；由服务层决定补派新单或转人工 | 「配送异常，已通知前台」 | 保洁人工配送（员工小程序任务） |
| 7 | 微信支付下单 | 超时、`upstream_error` | true | 用户可重试下单（同 `order_no` 幂等） | 「支付发起失败，请重试」 | 前台协助下单 |
| 8 | 支付回调验签 | 验签失败 | false | 返回 401，不写任何事实；告警排查 | 无（渠道侧重投） | 安全事件人工排查，必要时前台核单 |
| 9 | 支付回调丢失 | 长时间未收到成功回调 | — | 定时对账：主动查询支付状态补写事实 | 订单在支付后短时间自动进入已支付 | 超阈值未对平 → 前台人工核对流水后手动推进 |
| 10 | 微信登录 | `code` 失效 / 重复使用 | false | 前端重新触发登录获取新 `code` | 「登录已过期，请重新进入」 | 无 |
| 11 | 订阅消息下发 | 发送失败 / 未触达 | false | 不重试（主通道不受影响）；记录触达失败 | 订单页始终可见密码与指引 | 前台外呼告知（登记回访记录） |
| 12 | 每日密码轮换（批任务） | 部分房间设备失败 / 不可达 | false（批任务不自动重放） | 逐房独立事务：已生效房间保留；设备不可达即停止后续房间；任务失败关闭并给出计数 + 房间摘要（只含元数据） | 无（在住房本就跳过，客人无感） | 店长核对后经 `POST /api/admin/lock/rotation/run` 重跑（轮换幂等，重跑安全） |

原则：**任何 `retryable=false` 或重试耗尽的失败，都必须落到「用户可见结果或转人工」二者之一，不允许静默丢弃**；转人工一律经管理后台「人工接线」闭环（P7）。

## 9. P0.2 预研结论：可对接 / 需人工兜底清单

本结论基于 §1–§5 的协议形态、行业通用接口形态与 mock（`backend/app/device_sim`）演练得出，尚无真机环境。「可对接」= 接入路径明确，只需按厂商文档适配传输与签名，平台侧无阻塞；「需人工兜底」= 存在系统无法完全保证的环节，必须保留人工通道。

| # | 系统 / 能力 | 预研结论 | 依据（当前已验证范围） | 真机验证阶段 | 人工兜底方案 |
| --- | --- | --- | --- | --- | --- |
| 1 | 门锁凭证服务（签发 / 轮换 / 吊销） | 可对接 | §2 端点、幂等键、版本竞争 409、明文边界完整；mock 覆盖 error/timeout 恢复与重复调用 | P9（厂商 SDK/API 适配） | 见 §8-1/4：重试耗尽转前台手动签发；应急钥匙 |
| 2 | 门锁开锁记录 | 可对接（厂商支持回传时）；否则人工对账 | mock 提供解锁记录查询 | P9 | 门锁侧导出记录人工对账（§7-1） |
| 3 | 机器人配送 | 可对接 | §3 状态机与端点完整；`advance` 由厂商状态回调替代 | P9（失败码与回调协议） | 见 §8-6：failed 后补派或保洁人工配送 |
| 4 | 微信登录 | 可对接 | §4.1 标准 `code` 换 `openid` | P4 | 无（必选链路，无兜底） |
| 5 | 微信支付（下单 / 回调 / 对账） | 可对接 | §4.2 验签 + 幂等 + 乱序规则已定义；mock 覆盖重复投递与验签负例 | P9（APIv3 证书签名） | 见 §8-8/9：对账补偿 + 前台人工核单 |
| 6 | 订阅消息（密码下发第二通道） | 需人工兜底 | 模板审核、频率限制与触达率受微信侧约束（§7-4） | P4 落地链路（§4.4）；模板与触达率 P9 真机实测 | 密码主通道为订单页 / 站内消息；未触达时前台外呼 |
| 7 | PMS | 暂不对接（需人工兜底） | §5 仅登记范围，供应商未定 | P9（供应商确定后评估） | 房态与订单事实以 HaoChen 为准，前台人工与 PMS 同步 |

**无法对接项清单（预期即使 P9 也无法系统化，须长期保留人工通道）**：

- 门锁厂商若不提供开锁记录 API：开锁审计以门锁侧导出 + 人工定期对账替代（§9-2）。
- PMS 若无开放接口或无对接预算：房态与订单同步全人工（§9-7）。
- 订阅消息触达无法保证 100%：未触达用户一律走前台外呼（§9-6）。

以上三项在 P9 真机验证后逐项确认：能闭环的移出清单并在 §7 标记已验证；不能闭环的保持人工兜底并固化到运维手册。
