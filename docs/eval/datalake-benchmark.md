# 数据湖分析基准：PostgreSQL 直查 vs DuckDB 预聚合

日期：2026-10-17 · 对应 P3.3 · 原始结果：[datalake-benchmark.json](datalake-benchmark.json)

## 1. 业务问题与口径

同一条查询：「**各房型月度入住率与客单价**」。

- 有效订单：`paid / checked_in / checkout_pending / completed`，取消与未支付不计；
- 入住夜：按 `[check_in_date, check_out_date)` 逐夜展开，跨月订单按夜归属；
- 可售房晚：房型房间数 × 当月天数（当前库存快照，不回溯历史房态）；
- 入住率 = 已售房晚 / 可售房晚；客单价（ADR）= 房费收入 / 已售房晚，房费按夜均摊。

SQL 口径唯一实现在 `backend/app/data_pipeline/business_aggregates.py::build_room_type_monthly`；
两侧执行的是同一套口径的等价 SQL。

## 2. 方法与数据规模

基准脚本 `backend/bench_datalake.py`：

1. 生成确定性合成数据（seed 固定）；
2. 用生产管道同一函数生成预聚合 Parquet；
3. PostgreSQL 侧把同一批数据写入**会话级临时表**（不写业务库），直查展开入住夜后聚合；
4. 两侧各预热一次，重复 5 次取中位数；只统计查询耗时，不含数据导入与预聚合构建；
5. 逐行逐字段比对两侧结果（收入 ±0.01 分、入住率 ±1e-6）。

| 项 | 规模 |
| --- | --- |
| 订单 | **200,000** |
| 时间范围 | 12 个自然月 |
| 房型 / 房间 | 5 / 100 |
| 展开入住夜 | **425,403**（订单平均 2.17 晚） |
| 预聚合结果 | **60 行**（12 月 × 5 房型） |

环境：Windows 11（单机，同时运行整套 docker 服务）、Python 3.13.14、DuckDB 1.5.6、PostgreSQL 16.15。

## 3. 结果

| 路径 | 中位耗时 | min / p95 | 说明 |
| --- | --- | --- | --- |
| PostgreSQL 直查 | **568.43 ms** | 566.21 / 590.43 ms | 扫描 20 万订单 + LATERAL 展开 42.5 万入住夜 |
| DuckDB 预聚合 | **1.51 ms** | 1.39 / 1.58 ms | 直读 60 行 Parquet |
| 加速比（中位） | **≈ 378x** | —— | 结果逐字段一致，无差异项 |

复现：

```bash
cd backend
python bench_datalake.py --orders 200000 --months 12 --room-types 5 --rooms-per-type 20 --repeats 5 \
  --seed 42 --json-out ../docs/eval/datalake-benchmark.json
```

小规模冒烟（5,000 订单）中位耗时 34.00ms → 1.80ms（≈ 18.8x），方向一致但倍数更小，
说明**倍数随原始数据量增长**，引用时必须带规模。

## 4. 边界与诚实说明

- 该倍数代表「**固定口径、需扫描大量明细**」的报表查询；即席探索、小数据量或带高选择性过滤的查询不适用，
  预聚合缺失时系统按契约降级回 PostgreSQL 重算（口径一致，只是慢）。
- 基准只统计查询耗时：**不含**订单导出与预聚合构建的预处理成本，也不含查询时从 MinIO 下载 Parquet 的开销
  （基准直读本地文件；生产查询服务每次会下载必要分区）。
- PostgreSQL 侧用临时表且无二级索引，为全表扫描 + 逐夜展开；真实表虽有状态索引，但该查询形态以扫描为主，
  结论方向不受影响，具体毫秒数会随机器与并发变化。
- 合成数据为随机分布（状态权重、房价浮动），用于可比与可复现，不代表真实门店的入住分布。
- 单机、warm cache、无并发竞争；生产多租户并发下两侧都会变慢，倍数需要按环境复测。

## 5. 结论

数据湖预聚合路线在 20 万订单规模上把该业务查询从**百毫秒级降到毫秒级**（本机 378x），
且与 PostgreSQL 全量重算逐字段一致；README 的提速声明按此基准改写并标注数据规模。
